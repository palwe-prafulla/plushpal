# ToyTalk troubleshooting and debug guide

This guide is for technical users debugging a local ToyTalk checkout or a
locally built ToyTalk Hub package.

## Important paths

ToyTalk writes generated apps, release bundles, and test evidence outside the
source checkout.

```text
~/Downloads/ToyTalk/artifacts
~/Downloads/ToyTalk/release
~/Downloads/ToyTalk/test-results
```

ToyTalk Hub runtime data lives under macOS Application Support:

```text
~/Library/Application Support/ToyTalk
~/Library/Application Support/ToyTalk/logs
```

The most useful logs are:

```text
~/Library/Application Support/ToyTalk/logs/host.log
~/Library/Application Support/ToyTalk/logs/setup.log
~/Library/Application Support/ToyTalk/logs/app-shell.log
```

`host.log` contains Hub API, AI routing, latency, voice synthesis, pairing, and
runtime health details. `setup.log` covers dependency/model setup. `app-shell.log`
covers the macOS launcher shell.

## Privacy note for logs

Logs are local files on the Hub Mac. They must never contain API keys, SQLCipher
keys, raw audio bytes, session secrets, or full provider credentials.

For debugging, `host.log` may contain AI responses generated by Local AI,
Gemini, or OpenAI. These lines are tagged as `ToyTalk ai_response` and include
the selected mode/provider/model plus the spoken response. Treat logs as
private family/debug data before sharing them.

## Quick health checks

Open Hub, then run:

```sh
curl -s http://127.0.0.1:50076/api/v1/health | python3 -m json.tool
```

Useful log tails:

```sh
tail -100 "$HOME/Library/Application Support/ToyTalk/logs/host.log"
tail -100 "$HOME/Library/Application Support/ToyTalk/logs/setup.log"
tail -100 "$HOME/Library/Application Support/ToyTalk/logs/app-shell.log"
```

Useful greps:

```sh
grep "ToyTalk latency" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
grep "ToyTalk ai_response" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
grep "ToyTalk search_router" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
grep "cloud provider failure" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
grep "runtime mode" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -20
grep "LuxTTS" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
```

## Reading AI routing logs

Conversation success logs look like:

```text
ToyTalk latency request_id=... phase=conversation status=ok mode=cloud_llm provider=gemini model=gemini-... selected_mode=cloud_llm selected_provider=gemini selected_model=gemini-... generate_ms=...
ToyTalk ai_response request_id=... mode=cloud_llm provider=gemini model=gemini-... speech_chars=... suggest_trusted_adult=false speech_json="..."
```

Key fields:

- `selected_mode` / `selected_provider`: what the user selected.
- `mode` / `provider`: what actually generated the response.
- `conversation_local_fallback`: cloud failed and Hub used local AI fallback.
- `speech_json`: the locally logged spoken response.
- `generate_ms`: AI text generation time only.
- `ToyTalk search_router`: local current/live-info classification before
  AI routing. The classifier runs on every child turn. `needs_web_search=true`
  means Hub should avoid stale Local AI answers. Cloud AI may use provider
  search if the parent enabled Cloud AI web search; Local AI normally returns a
  grown-up fallback.
- `phase=hub_web_search`: Hub-owned evidence retrieval for Local AI current/live
  turns in the advanced env-backed path. `status=ok` means evidence was
  injected into the Local AI prompt;
  `provider_not_ready`, `insufficient`, or `hub_web_search_failed` means Hub
  failed safe instead of letting Local AI guess.
- `phase=voice`: LuxTTS synthesis time.

If `selected_provider=gemini` but `provider=local_ai`, Gemini failed and Hub
used local fallback. For current-data questions, ToyTalk should not fall back to
local AI; the local search router should mark `needs_web_search=true`. If web
Cloud AI web search is enabled, supported Cloud AI requests should include a
provider search tool. Local AI should return a grown-up fallback for
current/live questions unless the advanced Hub-owned evidence provider is
configured. If Cloud AI web search is disabled, Cloud AI answers should include
a double-check caveat and Local AI should return a grown-up fallback.

## Common technical issues

### Hub never becomes ready

Check:

```sh
tail -200 "$HOME/Library/Application Support/ToyTalk/logs/setup.log"
tail -200 "$HOME/Library/Application Support/ToyTalk/logs/host.log"
```

Look for:

- missing Python/venv setup;
- model download failure;
- LuxTTS worker load failure;
- local AI model install failure;
- search-router runtime/model install failure;
- health check timeout while a model is still loading.

If logs show model loading is still active, wait. If no progress appears, quit
Hub and reopen it. If voice runtime setup is corrupted, use Hub's reset voice
runtime action.

### Phone cannot pair

Check Hub is reachable on LAN:

```sh
grep "LAN bootstrap URL" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail
```

Then verify:

- phone and Mac are on the same Wi-Fi;
- Hub is open and ready;
- QR code is fresh;
- paired device is not revoked in Hub;
- phone has not kept a stale pairing session.

If Hub shows a paired phone but the phone says unpaired, revoke the phone in Hub
and pair again.

### Parent PIN or Cloud AI status mismatch

Parent PIN and Cloud AI keys are Hub-scoped encrypted data. Clients should not
own their own durable PIN/key state. If the client says setup is missing:

```sh
grep "provider/status\\|parent" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -50
```

Then reopen the client and Hub. If state is still inconsistent, re-pair the
client.

### Local AI gives weak or stale answers

Confirm selected and actual provider:

```sh
grep "ToyTalk latency" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -20
grep "ToyTalk ai_response" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -20
```

Local AI models are fully local but can be less current than Gemini/OpenAI.
ToyTalk classifies current/live questions before model routing. Turn on
Cloud AI web search in ToyTalk Hub if parents want supported Cloud AI providers
to use native web search for those turns. Local AI normally asks the child to
check with a grown-up for current/live information. For developer/power-user
Local AI evidence experiments, configure `TOYTALK_BRAVE_SEARCH_API_KEY`,
`PLUSHPAL_BRAVE_SEARCH_API_KEY`, or `BRAVE_SEARCH_API_KEY` in the Hub
environment before startup.

### Gemini/OpenAI answers are malformed or missing

Check provider failures:

```sh
grep "cloud provider failure" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -50
```

Likely causes:

- missing/invalid API key;
- provider HTTP error;
- provider ignored the structured-output schema;
- network unavailable;
- request timed out.

ToyTalk uses provider-native system instructions and structured output. If a
provider ignores the schema and returns a bare fragment, Hub rejects it and logs
the failure instead of treating it as a valid toy response.

### Speech-to-text works but there is no response

Check whether the turn reached Hub:

```sh
grep "phase=conversation" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
```

If there is no conversation log, the client did not send the command. If there
is a failed conversation log, check provider and fallback logs. If the response
is generated but no audio plays, check LuxTTS voice logs.

### Toy voice generation is slow

Check:

```sh
grep "phase=voice" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
grep "phase=voice_worker" "$HOME/Library/Application Support/ToyTalk/logs/host.log" | tail -30
```

`voice_worker` is the model/worker time. `phase=voice` is total synthesis and
response packaging time. Longer answers produce longer audio and higher latency.

### Android debug

With a connected Android device:

```sh
adb devices
adb logcat -d -t 3000 | grep "ToyTalk\\|flutter"
```

If pairing or speech fails, also check Android local-network/microphone
permissions and keep the screen unlocked during testing.

Run these before publishing changes:

```sh
cargo test --workspace
qa/automation/run_local_quality_gate.sh
make public-artifacts
```

Focused Hub/provider checks:

```sh
cargo test -p plushpal-policy-engine
cargo test -p plushpal-local-llm-llamacpp
cargo test -p plushpal-cloud-provider
cargo test -p plushpal-desktop-host --features native-runtime
```
